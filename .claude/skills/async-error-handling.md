# Async Error Handling\n\nStandards for propagating asynchronous failures, mapping domain exceptions to API responses, and keeping Express routes non-blocking.\n\n## When to Use\n\nReference this skill when implementing Express routes, middleware, store/service operations, error responses, or CPU-intensive backend work in `apps/api/`.\n\n---\n\n## Patterns\n\n### Centralize async propagation\n\nUse one `asyncHandler` wrapper so route handlers forward rejected promises to Express error middleware. Keep route handlers focused on orchestration rather than repeating `try/catch` blocks.\n\n```typescript\nimport type { NextFunction, Request, RequestHandler, Response } from 'express';\n\nexport const asyncHandler = (\n  handler: (req: Request, res: Response, next: NextFunction) => Promise<void>,\n): RequestHandler => (req, res, next) => {\n  void handler(req, res, next).catch(next);\n};\n\nrouter.get('/:id', asyncHandler(async (req, res) => {\n  const conference = await store.getConferenceById(req.params.id);\n  if (!conference) throw new NotFoundError('Conference not found');\n  res.json({ data: conference });\n}));\n```\n\nUse local `try/catch` only when the handler can meaningfully recover, translate a known low-level error, or add context before rethrowing. Never silently swallow an error.\n\n### Use typed operational exceptions\n\nCreate project-owned error classes with an HTTP status, stable public code, and optional safe details.\n\n```typescript\nexport class AppError extends Error {\n  constructor(\n    message: string,\n    public readonly statusCode: number,\n    public readonly code: string,\n    public readonly details?: unknown,\n  ) {\n    super(message);\n    this.name = new.target.name;\n  }\n}\n\nexport class NotFoundError extends AppError {\n  constructor(message = 'Resource not found') {\n    super(message, 404, 'NOT_FOUND');\n  }\n}\n\nexport class UnauthorizedError extends AppError {\n  constructor(message = 'Authentication is required') {\n    super(message, 401, 'UNAUTHORIZED');\n  }\n}\n\nexport class ValidationError extends AppError {\n  constructor(details: unknown, message = 'Validation failed') {\n    super(message, 400, 'VALIDATION_ERROR', details);\n  }\n}\n```\n\nThrow these errors from services/routes for expected operational failures. Do not use error classes for normal control flow such as an optional lookup.\n\n### Register one final error middleware\n\nRegister error middleware after all routes. It must preserve the standard envelope, log unexpected failures safely, and avoid leaking implementation details in production.\n\n```typescript\nimport type { ErrorRequestHandler } from 'express';\n\nexport const errorMiddleware: ErrorRequestHandler = (error, _req, res, _next) => {\n  if (error instanceof AppError) {\n    return res.status(error.statusCode).json({\n      error: {\n        message: error.message,\n        code: error.code,\n        ...(error.details === undefined ? {} : { details: error.details }),\n      },\n    });\n  }\n\n  console.error('Unhandled API error', error);\n  return res.status(500).json({\n    error: {\n      message: 'An unexpected error occurred',\n      code: 'INTERNAL_ERROR',\n    },\n  });\n};\n\napp.use('/api', apiRouter);\napp.use(errorMiddleware);\n```\n\n### Protect the event loop\n\nRoutes must yield to the event loop while waiting for I/O.\n\n- Prefer asynchronous database, filesystem, cryptography, and network APIs; always `await` their promises.\n- Keep JSON transforms, validation, and loops bounded. Paginate collections and impose request-size limits.\n- Move CPU-heavy work (large exports, image/video processing, password migrations, complex reports) to a worker thread or background job.\n- Set timeouts and cancellation/abort signals for outbound requests where supported.\n- Use `Promise.all` only for independent, bounded operations; preserve transaction ordering and concurrency limits where required.\n\n---\n\n## Anti-patterns\n\n```typescript\n// ❌ Repeated catch blocks that produce inconsistent errors.\nrouter.get('/:id', async (req, res) => {\n  try { /* ... */ } catch { res.status(500).json({ message: 'failed' }); }\n});\n\n// ✅ Let asyncHandler and errorMiddleware provide one response policy.\nrouter.get('/:id', asyncHandler(async (req, res) => { /* ... */ }));\n\n// ❌ Block the Node.js event loop in a request path.\nimport { readFileSync } from 'node:fs';\nconst data = readFileSync(path);\nwhile (expensiveCondition()) { /* long-running work */ }\n\n// ✅ Use async I/O or hand CPU-intensive work to a worker/job.\nconst data = await fs.promises.readFile(path);\n\n// ❌ Expose internal error text or stacks to clients.\nres.status(500).json({ error: { message: error.stack } });\n\n// ✅ Log internally and return a stable safe response.\nres.status(500).json({ error: { message: 'An unexpected error occurred', code: 'INTERNAL_ERROR' } });\n```\n\n---\n\n## References\n\n- `apps/api/src/app.ts`\n- `apps/api/src/server.ts`\n- `apps/api/src/routes/`\n- `apps/api/src/middleware/auth.ts`\n- `.claude/skills/backend-patterns.md`\n- [Express error handling](https://expressjs.com/en/guide/error-handling.html)\n- [Node.js event loop guidance](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)
